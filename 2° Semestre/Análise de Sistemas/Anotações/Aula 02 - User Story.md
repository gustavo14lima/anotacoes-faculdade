# 2. User Story

## 2.1 Definição da User Story

A User Story é uma ferramente fácil e simples de se utilizar, por ser uma ferramente bastante intuitiva. Ela serve como apoio para o levantamento de requisitos. Ela geralmente aborda uma descrição curta e simple sobre uma funcionalidade de um software, sendo contada a partir da perspectiva de quem vai utiliza-la, ou seja, o cliente. Ela é utilizada em uma linguagem mais natural e não muito técnica, pois o objetivo central dela é entrar valor ao cliente.

Ao final, quando uma User Story estiver validada, bem escrita e bem clara, ela será documentada, ou seja, esse requisito da User Story irá direto para o Product Backlog. Separados em requisitos funcionais e não funcionais.

## 2.2 Como escrever uma User Story

Uma User Story é escrita a partir de três pontos principais:
- Quem - É a definição do usuário, quem tem essa necessidade. Esse é um ponto crucial, pois é nessa pessoa quem iremos recorrer quando estivermos na fase de homolocação, ou seja, quem vai testar o requisito quando ele estiver pronto na aplicação. Ele te disso, quando a aplicação precisar de manutenção, por fim de registros, os desenvolvedores saberam quem pediu determinado requisito, assim, é possível verificar sua relevância quando atualizar a aplicação. Além de fazer um clareamento da User Story, ou seja, eu posso validar se é isso mesmo o que o cliente quer, se eu posso adicionar ou modificar algo, para que fique exatamente do seu agrado.
- O quê - Definição da necessidade do cliente. É aqui onde eu vou colocar as dores/necessidades que o meu cliente tem.
- Por quê - Define o motivo por trás desse requisito. Aqui é mostrado o valor desse requisito. Esse ponto é importante por causa que aqui saberemos quanto esse requisito é negóciavel, por exemplo, se ter outro requisito que agrega mais valor ao cliente, esse requisito com menor valor pode esperar um pouco. 

### 2.2.1 Estrutura para escrever uma User Story

Eu (nome de quem está pedindo o requisito), enquanto (QUEM - primeiro ponto da explicação acima), quero (O QUÊ - segundo ponto da explicação acima), para (POR QUÊ - terceiro ponto da explicação acima).

Exemplo:
- Eu Roberto, enquanto proprietário de um site de vendas, quero um sistema que traga segurança no cadastro de clientes no meu Market place, para atender a LGPD.

## 2.3 Metodologia INVEST

Quando uma User Story parece muito ampla e genérica, ou seja, quando posso ter mais de uma interpretação, possa ser que no meio do desenvolvimento acabe tendo dúvidas sobre o que deve ser feito por estar muito vago. Esse problema é resolvido por a metodologia INVEST.

A metodologia INVEST é uma validação de User Story, como se fosse uma checklist para verificar se uma User Story está bem escrita e pronta para ser documentada. Ele garante que a  necessidade do usuário seja  uma necessidade real de negócio sem se transformar em um documento técnico pesado ou em um "Épico" genérico (uma User Story muito grande, muito vaga e muito ampla).

O checklist da metodologia INVEST funciona da seguinte maneira:
- **I**ndependente - Não depende de outros requisitos para que seja feita ou para  funcione corretamente. Ela não pode depender de outro requisito para começar a ser feita.
- **N**egociável - Esse requisito pode ser negociável, ou seja, pode ser alterado, pode ser remarcado e etc.
- **V**alioso - Aqui verificamos se o requisito é realmente valioso para o projeto do cliente. Verifica-se se o usuário terá melhorias ou ganhos com esse requisito.
- **E**stimável - Eu consigo estivar quanto tempo eu irei gastar ou demorar para fazer esse requisito.
- **S**mal (Pequeno) - Verifico se esse requisito é pequeno para ser feito, se não será muito trabalhoso ou se irá ser dividido em outros requisitos.
- **T**estável - Verificar se é possível testar ou não esse requisito. Saber se ele passa por algumas validações/regras para designar se ele funciona ou não.

## 2.4 Método Slice

Quando temos uma User Story Épica, ou seja, uma User Story muito ampla, muito grande e que pode ser intepretada de diferentes maneiras, utiliza-se o método Slice.
O método Slice quebra a User Story Épica em várias outras User Storys, assim, deixando elas menores, o que por sua vez, facilita no desenvolvimento e entendimento do requisito.
