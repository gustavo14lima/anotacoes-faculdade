# 3. Lean UX Canvas

## 3.1 Refresh últimas aulas

As regras de negócios estão ligadas ao funcionamento de um sistema, explicando como exatamento o sistema deve atuar e agir. As regras de negócios também podem atuar no processamento de dados, de acordo com as diretrizes das regras. E as regras de negócio executam o sistema de acordo como foi específicado nas diretrizes das regras de negócio.

Na Análise de Sistemas, passamos por 6 (seis) importantes passos antes da criação de um software, sendo eles:
- Identificar problemas - Você reconhece e define os problemas que precisam ser resolvidos
- Levantar requisitos - Começo a coletar informações sobre as necessidades e expectativas dos meus usuários.
- Investigar soluções - Começo a explorar diferentes abordagens para resolver o problema do meu usuário. 
- Específicar Soluções - Começo a detalhar os requisitos e especificações da solução.
- Criar software - Desenvolvo o software com base nas minhas pesquisas e com o objetivo de suprir a necessidade do meu usuário.
- Implementar Software - Integrar o software ao seu devido ambiente.

Os requisitos funcionais são aqueles que focam nas funcionalidades essenciais para a utilidade e os requisitos não funcionais focam nos aspectos essenciais para a qualidade do sistema. 

Quando eu inicio a análise de requisito, primeiro eu começo elicitando os requisitos do negócio e do usuário, após isso eu começo a separar os meus requisitos funcionais e não funcionais (a partir dos meus requisitos de usuários) e por fim, eu defino os requisitos de sistema.

As Users Storys são descrições curtas e simples sobre as funcionalidades que o meu sistema deve conter. Ela é escrita na perspectiva do usuário, sempre dando valor a entrega. E o mais importante, ela é escrita em uma linguagem natural e sem muito termos técnicos. Eu escrevo uma User Story seguindo os três pilares:
- Quem? - Define quem pediu esse requisito, ideal ter nome e cargo.
- O quê? - Define a necessidade do cliente.
- Por quê? - Define para que ser e para que será utilizada esse requisito, sempre focando na entrega de valor.

Lembrando que no final, toda User Story vai parar no Product BackLog separadas com Requisito Funcional e Requisito Não Funcional.

## 3.2 Lean UX Canvas

O Lean UX Canvas é outra ferramenta de análise de sistemas. Ela é uma ferramenta fácil de utilizar e bem adaptativa. Ela é uma abordagem de design que prioriza a experimentação rápida, a valiação de hipoteses e a entrega contínua de valor ao usuário. O Lean UX Canvas foca em aprender e corrigir rapidamente, levando em considareção os feedbacks recebidos pelo usuário.

A Lean UX Canvas junta combina alguns principios, sendo um deles é o Design Thinking e a metodólogia ágil, que foca em otimizar os processos de design e desenvolvimento de produtos, foca na criação de ciclo contínuos de serviços, no qual, pode ser utilizado para construir, ajustar, aprender e entre outros, com o feedback real do usuário. 

O Design Thiking tem uma semelhança maior com a metodólogia em castaca, que precisa que um requisito/processo seja finalizado por inteiro para que possa começar a desenvolver o próximo requisito/processo. Ela é uma abordagem de inovação centralizada no ser humano, usada para resolver os problemas complexos de maneira criativa e colaborativa. Diferente do Lean UX Canvas, ela possui um olhar centralizado na experiência do usuário e na resolução real do problema. 

O Lean UX Canvas é um apoio para o levantamento de problemas e necessidades dos clientes, alinhamento com negócio e TI, facliita o aprendizado rápido e tomada de decisão com base nas evidências.

## 3.2 Construção do Lean UX Canvas

A construção do Lean UX Canvas é com base em 5 (cinco) blocos principais:
- Problema do negócio 
	- Dor atual do cliente - Explicar a situação atual que o usuário se encontra atualmente, explicar o que está acontecendo para isso ser um problema.
	- Impacto para o negócio - Explicar o motivo do por que isso é um problema para a empresa.
	- Contexto - Explicar como e por que o comportamento do mercado ou do usuário muda com este problema.
- Benéficios para o negócio
	- Explicar todo o impacto e valor que, a paritr de uma solução, a sua empresa terá depois de suprir o problema
- Usuários
	- Escrever quem são os usuários do seu serviço, ou seja, quem compra e utiliza o seu serviço, quem configura o seu serviço. Em outras palavras, mostrar todos que estão interligados com o seu serviço, e que podem ser afetados pelo problema.
- Benéficios para o usuário 
	- Aqui é onde você explicar qual é o valor que o seu usuário, ou seja, que está usando, terá após o problema ser resolvido. Por exemplo, o que o usuário ganha após o problema ter sido resolvido.
	- Lembre-se que nem tudo se resumo a ganhos tangíveis, mas em alguns casos, possa haver ganhos intangíveis, como por exemplo, a sua aplicação ficou melhor e mais simples de ser usuada, assim, os usuários iram recomendar sua aplicação para que outros usuários possam a utilizar sua aplicação.
- Soluções 
	- Aqui eu explico qual é a melhor forma, e mais rápida e simples, de resolver o problema do usuário, além de garantir que essa resolução de problema irá trazer algum valor para o usuário (sendo ele intagível ou tangível) e também testar se o usuário realmente irá usar.
	- Em outras palavras, aqui eu vou explicar como eu vou resolver o problema do usuário. 

No final do dia a contrução da uma Lean UX Canvas ficará dessa maneira:

| Problema do negócio | Soluções | Benéficios para o negócio     |
| ------------------- | -------- | ----------------------------- |
|                     |          |                               |
| **Usuários**        |          | **Benéficios para o usuário** |
|                     |          |                               |

## 3.3 Lean UX Canvas + User Story

Uma boa estratégia para escrever uma Lean UX Canvas é a partir das anotações que capturamos com a User Story. Pois nela temos as informações necessárias para escrever sobre o problema e os usuários. O seu trabalho será apenas em pensar em como solucionar o problema e dissertar sobre os benéficios de solucionar esse problema.

Além disso, quando eu junto o Lean UX Canvas com User Story eu consigo dar voz e perspectiva ao problema e necessidades do usuário. É possível traduzir as necessidades do usuário para uma linguagem natural, assim facilitando o seu desenvolvimento. Ambos as metodólogias podem ser negociavel, priorizadas de acordo com a necessidade e desejo do usuário. Eu consigo observar um valor para o negócio que eu estou contruindo. Garanto que com uma boa específicação dos meus requisitos, eu posso agilizar o time de desenvolvedores, por causa que os requisitos não seram ambuigos ou causarem problemas. E por fim, podemos criar uma ponte entre o problema do usuário e a solução técnica desse respectivo problema.
